# agent-boards の設計

コーディングエージェントが人に何かを見せるための窓を、1 つのリポにまとめたもの。使い方は各コマンドの文書（[moodboard](moodboard.md)・[textboard](textboard.md)・[reportboard](reportboard.md)）を見る。この文書は、どう分けてどう作るかの決まりだけを書く。

出典の書き方: 「ユーザーの判断」はユーザーが決めたこと、「Claude の判断」は実装した Claude が決めたこと。

## リポの構成

- 1 リポ・1 パッケージ。`package.json` の `bin` に `moodboard`・`textboard`・`reportboard` の 3 つを並べる（ユーザーの判断。3 つが別々のリポにばらけるのを避けるため）
- リポ名は `agent-boards`（ユーザーの判断）
- `moodboard`・`textboard` のコマンド名・引数・挙動は統合前と変えない（ユーザーの判断）。`--target`・`--json`・`wait`・`--close`・`--list`・`--lang` と終了コードも含む
- エントリの `.ts` と、窓に出す `.html` はリポの直下に置く（Claude の判断。統合前と同じ相対位置にして、`.html` を探す処理を変えずに済ませるため）
- スキルは `skills/moodboard`・`skills/textboard`・`skills/reportboard` の 3 つに分ける（ユーザーの判断）。インストールは `bun install -g github:mohhh-ok/agent-boards` で 3 つのコマンドがまとめて入る
- 統合前の 2 リポの git の履歴は、`--allow-unrelated-histories` のマージで残している（Claude の判断）。両方にあった README と開発メモは `docs/<コマンド名>.md`・`docs/<コマンド名>-development.md` に移した

## 共通の部品

2 つのコマンドに同じものが書かれていた部品は `lib/` に 1 つだけ置き、3 つのコマンドがそれを使う（ユーザーの判断）。

- `lib/lang.ts`: 表示言語の決め方（`--lang` > `<コマンド名>_LANG` > macOS の言語設定。ja 以外は en）と、言語ごとのメッセージ表の切り替え
- `lib/outbox.ts`: 窓から AI への送信の受け渡し（outbox への書き込み・`wait` での受け取り・AI が `wait` しているかの印）。textboard と reportboard が使う
- `lib/windows.ts`: `--target` の窓の管理。状態ディレクトリ（`/tmp/<コマンド名>-<uid>/`、権限 700 と持ち主の確認）・名前ごとのロック・pid ファイルと「その pid が今もこのコマンドの窓か」の確認・差し替え要求・ack の受け渡し・新しい窓のプロセスの起動・`--close`・`--list`・古いファイルの掃除・窓のプロセスの後片付け・ページの URL の組み立て

各コマンドに残すもの: 引数の解釈、メッセージの文言、窓に渡す中身（moodboard の board・textboard のファイルとコメント・reportboard の描画済み HTML）、ページと結ぶ関数（`__<コマンド名>Load` など）。

- 状態ディレクトリはコマンドごとに分けたままにする（ユーザーの判断。今開いている窓や既存の状態ファイルと衝突させないため）
- 共通化で挙動が変わる箇所は変えずに、実装者が親セッションに報告する（ユーザーの判断）
- 「その pid が今もこのコマンドの窓か」は、プロセスの引数が「同じファイル名のスクリプト・`--window`・その名前の target」かで見る。スクリプトの置き場所（グローバルのインストールか、リポの作業コピーか）は問わない（Claude の判断）。以前は置き場所まで一致を求めていた。そのため、リポから動かした `--list` がグローバル版で開いた窓の pid ファイルを消し、次の `--target` で同じ名前の窓が 2 つ開いた。逆に、グローバル版の `--list` も、リポから開いた窓の pid ファイルを消していた。どちらの置き場所の版も、同じ状態ディレクトリを使う
- pid ファイルが無いか、別のプロセスを指しているときは、動いているプロセスの一覧からその名前の窓を探す。見つかれば pid ファイルを書き直し、新しい窓は開かない。`--list` も、動いているプロセスの一覧から見つけた窓を出す。pid ファイルを消すのは、その名前の窓が 1 つも動いていないときだけ（Claude の判断。pid ファイルがどんな理由で消えても、同じ名前の窓を二重に開かないため）
- 同じ名前への起動が重なったときに、ロックの確認中に落ちる不具合は、統合前の moodboard・textboard の両方にあったが、利用者全員に起こりうるので直した（親セッションの Claude の判断）

## reportboard

計測・調査・見積もりのレポートを人に見せる窓（ユーザーの判断）。

- 呼び方: `reportboard [--lang ja|en] [--target <名前>] <file.md>`・`wait`・`reply`（下の「セクションごとに AI とやり取りする」）・`--close <名前>`・`--list`。`--target` の意味は moodboard と同じで、同じ名前の窓があれば中身を差し替える（ユーザーの判断）
- 入力は Markdown（GFM の表を含む）。見た目は道具の側で 1 つに固定し、呼ぶ側は見た目を指定しない（ユーザーの判断）
- 開いているファイルが書き換わったら、窓が自動で読み直す。スクロール位置は保つ（Claude の判断）
- Markdown の描画は窓のプロセス（Bun）で `marked` を使って行い、ページには描画済みの HTML を渡す（Claude の判断。描画の規則を bun test で確かめられるようにするため）

### セクションごとに AI とやり取りする

ユーザーの発言（逐語）:「aiにしじできるようにしたいねん。該当セクションのボタンをクリックすると、そこでaiとやり取りができるって言うの」

親セッションの Claude の判断（上の発言の「そこで」「やり取り」から）:

- やり取りは往復にする。AI の返事は、ボタンを押したセクションの中にスレッドとして出す。ユーザーは同じスレッドで続けて送れる
- AI は返事を送るコマンドで返す。md を直したときも、何を直したかを返事に書く
- スレッドは、窓の差し替えや md の読み直しで消えない場所に持つ
- `wait` が返す JSON に、スレッドの id とそのスレッドの過去のやり取りを含める
- ボタンは h2 と h3 の見出しごとに置く。内訳の行ごとには置かない（ユーザーが言っていないため）
- 窓から AI への送信・`wait`・「AI が待っているか」の表示は textboard と共通の部品（`lib/outbox.ts`）にする

実装の Claude の判断:

- 呼び方: 窓で送った指示は `reportboard wait --target <名前> [--timeout <秒>]` が受け取る。返事は `reportboard reply --thread <id> <本文>`（本文の代わりに `--file <path>` でファイルから読める）。スレッドの id で保存先が決まるので、`reply` に `--target` は要らない。窓を閉じていても返事は保存され、次に開いたときに出る
- ボタンは名前付きの窓（`--target`）だけに出す。名前の無い窓は `wait` で受け取る相手を指定できないため
- 保存先は `~/.reportboard/threads/<md の絶対パスの sha256>.json`（`REPORTBOARD_HOME` で `~/.reportboard` を変えられる）。md の隣に置かないので、ユーザーのリポにファイルが増えない。md を移動・改名するとスレッドは外れる（textboard のコメントと同じ扱い）
- スレッドと見出しの対応: スレッドは見出しの文字列と階層（h2/h3）を持つ。読み直しのたびに、同じ文字列・同じ階層の見出しに付け直す。同じ見出しが複数あるときは何番目かで合わせる。見出しが変わって合うものが無くなったスレッドは消さず、本文の最後の「見出しが見つからないやり取り」に出す。AI が `reply` すると、そのスレッドは返事の時点の見出しのまま残る
- 送信は Enter、改行は Shift+Enter（textboard と同じ）

ユーザーの発言（逐語）:「「aiに聞く」って、きけるだけなん？編集とかも含めてやりとりしたいんだけど」

親セッションの Claude の判断:

- ボタンの文言は「AI と直す」（英語は「Edit with AI」）
- AI の手順は「送られた内容が直しの指示なら md を書き換え、質問なら答える。どちらもスレッドに返事を書き、直したときは何を直したかを書く」。編集を質問のついで扱いにしない
- 窓の中の、質問だけを想定した文言もあわせて直す
- スレッドのファイルの読み書きは、ファイルごとのロックの中で行う。窓からの送信と `reply` が同時でも、どちらのメッセージも消さない（親セッションの Claude の判断）
- 既知の制限: 同じ md を 2 つの名前の窓で開き、同じ見出しで初めて送ると、スレッドが 2 つでき、窓には片方しか出ない。今回は直さない（親セッションの Claude の判断）

### 受け取った合図と、返事を分けて出す

ユーザーの発言（逐語、時系列）:

- 「あとさ、このreportboard,返信はストリーミングでりあるたいむででるようにはむりかな」
- 「cliでおくるかわりに、ファイルにかきこんでいくのはむりなんか？」
- 「まぁ、できるだけ分割ででてくるようにしてよ。状況が変わらないとふあんになる」

親セッションの Claude の判断:

- 返事を 1 文字ずつ流すことはできない。Claude Code は返事を書き終えてからツールを 1 回呼ぶので、`reply` でもファイルへの書き込みでも、届くのは呼んだ回ごとのまとまりになる
- 代わりに、`wait` がメッセージを受け取った時点で、窓のそのスレッドに AI が受け取ったと分かる表示を出す。受け取り待ちの AI がいないときの案内文とは区別する
- 作業中の表示は、受け取ってから「`reply` に `--done` を付けたとき」か「AI が次の `wait` を始めたとき」の早い方まで残す。`--done` を付け忘れても次の `wait` で消えるので、出しっぱなしにならない。途中の `reply` が届いても残し、最新の返事の下に出す。途中報告と結果の間も作業中だと見えるようにするため（ユーザーの「状況が変わらないとふあんになる」に沿う）。最初は「最初の返事で消す」としていたのを、これに変えた
- `reply` は同じスレッドに何回送ってもよい。スキルの手順を「受け取ったらすぐ何をするかを短く返す → 作業の区切りごとに途中を返す → 最後に結果を `--done` 付きで返す」にする。状況が長く変わらないと使う人が不安になるため（ユーザーの発言）

実装の Claude の判断:

- `wait` が渡したメッセージに、スレッドのファイルで受け取った時刻（`receivedAt`）を書く。窓はスレッドのファイルの変化を読み直しているので、合図はすぐ出る。窓を開き直しても残る
- `reply --done` は、そのスレッドで受け取り済みのユーザーのメッセージに `doneAt` を書く。`wait` は始まった時刻を状態ディレクトリの `targets/<名前>.wait-started` に書き、窓はこれが変わったらスレッドを読み直す
- スレッドの状態はユーザーの最新のメッセージで決める。AI がまだ受け取っていない＝入力欄の下に「送りました」。受け取って返事がまだ＝会話欄の末尾に AI の名前で「受け取りました。返事を書いています」の行（点が動く）。返事が届いた後も作業中＝最新の返事の下に、名前を出さず「作業を続けています」の行。`doneAt` があるか、受け取った後に `wait` が始まっていれば表示なし。作業中は入力欄の下の案内も「AI が作業中です」にする（`wait` は受け取った時点で終わるので、「受け取り待ちではありません」と出すと実態と違うため）
- 続けて届いた AI の返事は 1 つのまとまりに見せる（2 通目以降は名前を出さず、時刻だけ出す）

### 会話欄は左右に分けたチャットにする

ユーザーの発言（逐語）:「あと、reportboardは、よくあるチャットUIにしてくれるかな。みぎとひだりでわけるやつ」

親セッションの Claude の判断:

- セクションと内訳の行の会話欄で、使う人が送ったものを右、AI の返事を左に寄せた吹き出しにする
- 「受け取りました。返事を書いています」「作業を続けています」は AI 側（左）に出す
- textboard には会話の表示が無いので、reportboard だけを変える

実装の Claude の判断:

- 吹き出しは角丸 8px の四角にし、話し手の側の上の角だけ 2px にして、誰の発言かを向きでも示す。角丸ピル形にはしない
- 使う人の吹き出しはアクセント色を薄くした面、AI の吹き出しはページの地色に枠線。会話欄の地（`--bar-bg`）の上で、どちらも本文と同じ文字色で読める
- 左右で誰の発言か分かるので、使う人の名前（「あなた」）は画面に出さず（読み上げには残す）、時刻だけ出す。AI は続けて届く返事の 1 通目だけ名前を出し、2 通目以降は時刻だけにして間を詰める
- 「受け取りました」「作業を続けています」は、返事の吹き出しと同じ形で枠を点線・文字を薄い色にし、届いた返事と区別する
- 吹き出しの幅は会話欄の 85%（最大 46em）まで。区切り線は使わない
- 会話欄の高さの上限を 15em から 20em にした。吹き出しは余白の分だけ縦に伸びるため
- 内訳の行の会話欄は、行の内側の余白の分だけ外へ広げ、見出しの会話欄と左右の端・送るボタンの位置をそろえる（UI チェックの指摘）
- 返事が届いて会話欄が伸び、入力欄が窓の下へ押し出されるときは、伸びる前に入力欄が一部でも窓の中に見えていた場合だけ、伸びた分ページを送る。読み返している人の画面を勝手に動かさないため（UI チェックの指摘）
- 目次の強調: 「一番下まで送ったら最後の見出し」の決まりは、スクロールしたときだけ使う。窓より短いページの先頭で最後の見出しが強調されていたため。会話欄や行を開いてページの高さが変わったときも計算し直す（UI チェックの指摘）

### 直す対象

Claude が手書きした見積もりレポートの HTML で、ユーザーが認めた見にくい点（ユーザーの判断）と、reportboard での直し方（Claude の判断）。

1. 本文の幅が 860px 固定で、PC 幅では左右が空いたまま縦に長く伸び、11 項目を見るのに 2 画面以上スクロールが要った
   - 幅を窓に合わせて広げる。広い窓では左に見出しの目次を置く。地の文だけは読みやすい行長で止め、項目の一覧と表は幅いっぱいに使う。項目の内訳は 2 行で畳み、押すと開く
2. 内訳の人日が行末の数字に埋もれ、どれが重いか目で拾えなかった
   - 「名前 — 数値 単位。説明」の形の箇条書きが 2 つ以上並ぶ一覧は、数値を行の先頭の列に大きく出し、一覧の中の最大値に対する長さの棒を添える
3. 注記がピンクがかった灰色の小さい字で読みにくかった
   - 注記（引用・括弧書きの補足）も本文と同じ大きさ・十分なコントラストの色にする
4. 項目名と区分・人日が左右の端に離れ、目を往復させた
   - 数値・項目名・説明を左から隣り合わせに並べ、間を空けない

見た目は既定の型をなぞらない。クリーム色の背景、見出しの一語だけの斜体、01/02/03 の番号見出し、等幅フォントのラベル、角丸ピル形のボタンは使わない（ユーザーの全体方針）。

## やらないこと（親セッションがユーザーに確認してから行う）

GitHub のリポ作成と push、統合前のリポのアーカイブ、`bun install -g` での入れ替え、`~/.agents/skills/`・`~/.claude/skills/`・`~/Dev/agent-config` の変更。
